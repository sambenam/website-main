# قرارداد API — راهنمای تیم بک‌اند

این سند تنها چیزی است که برای وصل کردن این فرانت‌اند به سرور لازم دارید.

---

## خلاصه یک‌دقیقه‌ای

کل پروژه از یک لایه واحد به نام `appApi` (در `scripts/api.js`) برای تمام دسترسی‌های داده استفاده می‌کند. هیچ فایل دیگری مستقیماً `localStorage` یا `fetch` صدا نمی‌زند.

**`scripts/api.js` فقط ۴۰۳ خط است و همه‌اش مال شماست** — تنظیمات، تابع `fetch`، و فهرست کامل مسیرها. هیچ منطق کسب‌وکاری داخلش نیست.

سرور شبیه‌سازی‌شده در سه فایل جداست که **قرار است حذف شوند، نه ترجمه**:

| فایل                |  خط | نقش                                        |
| ------------------- | --: | ------------------------------------------ |
| `api-mock-store.js` | ۱۵۸ | کلیدهای localStorage و کمک‌کننده‌های مشترک |
| `api-mock-site.js`  | ۵۰۸ | مسیرهای عمومی سایت                         |
| `api-mock-admin.js` | ۵۴۵ | مسیرهای پنل ادمین                          |

این سه را مثل **سند مشخصات** بخوانید: هر ورودی که می‌پذیرند، هر خروجی که می‌دهند و هر خطایی که می‌اندازند، همان قراردادی است که سرور واقعی باید رعایت کند.

در حالت فعلی `mode: "mock"` است و داده‌ها در `localStorage` می‌مانند. برای وصل شدن به سرور واقعی:

```html
<!-- در <head> هر صفحه، قبل از api.js -->
<script>
  window.APP_CONFIG = {
    apiMode: "real",
    apiBaseUrl: "https://api.example.com",
  };
</script>
```

و سه خط زیر را از انتهای هر صفحه پاک کنید:

```html
<script src="../scripts/api-mock-store.js"></script>
<script src="../scripts/api-mock-site.js"></script>
<script src="../scripts/api-mock-admin.js"></script>
```

همین. هیچ فایل جاوااسکریپت دیگری نیاز به تغییر ندارد. `api.js` بدون فایل‌های موک هم کار می‌کند — نگهبانی در انتهای آن هست که وقتی موکی پیدا نکرد، مستقیم سراغ `fetch` می‌رود.

جایگزین دیگر (برای تست سریع بدون تغییر کد):

```js
localStorage.setItem("hesabyarApiMode", "real");
localStorage.setItem("hesabyarApiBaseUrl", "https://api.example.com");
```

## قواعد عمومی

| مورد         | قرارداد                                                                 |
| ------------ | ----------------------------------------------------------------------- |
| Base URL     | از `APP_CONFIG.apiBaseUrl` خوانده می‌شود                                |
| Content-Type | `application/json`                                                      |
| احراز هویت   | هدر `Authorization: Bearer <token>` — توکن از پاسخ `/auth/login` می‌آید |
| Timeout      | ۱۰ ثانیه (سمت کلاینت)                                                   |
| موفقیت       | کد ۲xx به‌همراه بدنه JSON                                               |
| خطا          | کد غیر ۲xx به‌همراه `{ "message": "متن فارسی خطا" }`                    |

### قالب خطا

فرانت‌اند فیلد `message` را مستقیماً به کاربر نشان می‌دهد، پس متن آن باید فارسی و قابل‌فهم باشد:

```json
{ "message": "ایمیل یا رمز عبور صحیح نیست." }
```

کدهای وضعیتی که فرانت‌اند به‌طور خاص مدیریت می‌کند:

| کد    | معنا در این پروژه          |
| ----- | -------------------------- |
| `401` | نیاز به ورود مجدد          |
| `409` | تعارض — مثلاً شناسه تکراری |
| `422` | خطای اعتبارسنجی ورودی      |
| `404` | منبع پیدا نشد              |

## اندپوینت‌های عمومی (سایت)

### احراز هویت

| متد    | مسیر                    | بدنه درخواست                       | پاسخ                   |
| ------ | ----------------------- | ---------------------------------- | ---------------------- |
| `POST` | `/auth/register`        | `{ name, email, phone, password }` | `{ token, user }`      |
| `POST` | `/auth/login`           | `{ email, password }`              | `{ token, user }`      |

## اندپوینت‌های پنل مدیریت

همه این مسیرها نیازمند نشست ادمین هستند. سرور باید بدون توکن معتبر، `401` برگرداند.

### محصولات

| متد      | مسیر                  | بدنه               | پاسخ                |
| -------- | --------------------- | ------------------ | ------------------- |
| `GET`    | `/admin/products`     | —                  | آرایه محصولات       |
| `POST`   | `/admin/products`     | آبجکت محصول        | محصول ساخته‌شده     |
| `PATCH`  | `/admin/products/:id` | فیلدهای تغییریافته | محصول به‌روزشده     |
| `DELETE` | `/admin/products/:id` | —                  | `{ success: true }` |

شکل محصول:

```json
{
  "id": "course-1",
  "name": "دوره حسابداری مقدماتی",
  "price": 49000,
  "category": "file",
  "fileUrl": "https://...",
  "img": "https://..."
}
```

**قواعد:** `id` و `name` الزامی‌اند. `id` تکراری باید `409` بدهد.

> نکته درباره `id`: صفحه تک‌مطلب با قرارداد نام‌گذاری محصول را به مطلب وصل می‌کند — `<postId>` برای فایل‌ها و `<postId>-video` برای ویدیو. این قرارداد را حفظ کنید.

### سفارشات

| متد     | مسیر                       | بدنه         | پاسخ            |
| ------- | -------------------------- | ------------ | --------------- |
| `GET`   | `/admin/orders`            | —            | آرایه سفارشات   |
| `POST`  | `/admin/orders`            | آبجکت سفارش  | سفارش ساخته‌شده |
| `PATCH` | `/admin/orders/:id/status` | `{ status }` | سفارش به‌روزشده |

مقادیر مجاز `status`: `success` · `pending` · `cancelled`

### کاربران

| متد      | مسیر                      | بدنه         | پاسخ                |
| -------- | ------------------------- | ------------ | ------------------- |
| `GET`    | `/admin/users`            | —            | آرایه کاربران       |
| `PATCH`  | `/admin/users/:id/status` | `{ status }` | کاربر به‌روزشده     |
| `DELETE` | `/admin/users/:id`        | —            | `{ success: true }` |

شکل کاربر:

```json
{
  "id": 12,
  "name": "مریم حسینی",
  "email": "maryam@example.com",
  "phone": "09121234567",
  "role": "کاربر عادی",
  "status": "فعال",
  "source": "site"
}
```

مقادیر `role`: `کاربر عادی` · `ادمین` · `مدیر سایت` · `مدیر سیستم`
مقادیر `status`: `فعال` · `غیرفعال`

> **مهم:** پاسخ این مسیر باید شامل کاربرانی باشد که از طریق `/auth/register` در سایت ثبت‌نام کرده‌اند. فیلد `source` مشخص می‌کند کاربر از سایت آمده (`site`) یا در پنل ساخته شده.

### پیام‌ها

| متد     | مسیر                        | بدنه                  | پاسخ                  |
| ------- | --------------------------- | --------------------- | --------------------- |
| `GET`   | `/admin/messages`           | —                     | آرایه پیام‌ها         |
| `POST`  | `/admin/messages/:id/reply` | `{ text, adminName }` | پیام با ترد به‌روزشده |
| `PATCH` | `/admin/messages/:id/read`  | —                     | پیام به‌روزشده        |

شکل پیام:

```json
{
  "id": "message-...",
  "sender": "سام به‌نام",
  "email": "sam@example.com",
  "subject": "سوال درباره دوره",
  "text": "متن پیام کاربر",
  "time": "۱۴۰۵/۰۵/۰۵",
  "read": false,
  "source": "site",
  "history": [
    { "sender": "user", "name": "سام به‌نام", "text": "...", "time": "..." },
    { "sender": "admin", "name": "مدیر سایت", "text": "...", "time": "..." }
  ]
}
```

`history` ترد گفتگو است و به‌ترتیب زمانی مرتب می‌شود. مقدار `sender` فقط `user` یا `admin`.

### تنظیمات

| متد   | مسیر              | بدنه               | پاسخ              |
| ----- | ----------------- | ------------------ | ----------------- |
| `GET` | `/admin/settings` | —                  | آبجکت تنظیمات     |
| `PUT` | `/admin/settings` | فیلدهای تغییریافته | تنظیمات ادغام‌شده |

شکل تنظیمات:

```json
{
  "supportEmail": "support@example.ir",
  "supportPhone": "۰۲۱-۱۲۳۴۵۶۷۸",
  "maintenanceMode": false,
  "merchantId": "...",
  "currencyUnit": "toman",
  "adminName": "مدیر کل سایت",
  "adminAvatar": "https://..."
}
```

`PUT` باید **ادغام** کند نه جایگزینی کامل — ارسال `{ maintenanceMode: true }` نباید بقیه فیلدها را پاک کند.

`supportEmail` و `supportPhone` در فوتر تمام صفحات سایت نمایش داده می‌شوند.
`maintenanceMode: true` کل سایت عمومی را قفل می‌کند (پنل ادمین مستثنی است).

## نکات امنیتی که سمت سرور باید رعایت شود

فرانت‌اند نمی‌تواند این‌ها را تضمین کند:

1. **احراز هویت پنل ادمین.** در حال حاضر یک گیت سمت کلاینت در `scripts/admin/auth.js` (تابع `requireAdminSession`) وجود دارد که فقط جلوی دسترسی تصادفی را می‌گیرد. سرور باید بدون نشست معتبر، هم فایل `admin.html` و هم تمام مسیرهای `/admin/*` را رد کند.

2. **رمز عبور.** رمز ادمین در حال حاضر در `localStorage` است چون بک‌اندی وجود ندارد. با آمدن سرور، بدنه تابع `verifyAdminPassword` را با یک درخواست به سرور جایگزین کنید. رمزها باید هش شوند (bcrypt یا argon2).

3. **اعتبارسنجی ورودی.** تمام اعتبارسنجی‌های سمت کلاینت صرفاً برای تجربه کاربری‌اند و باید سمت سرور تکرار شوند.

4. **پاک‌سازی خروجی.** پنل در جاهایی از `innerHTML` استفاده می‌کند. داده‌ای که از سرور می‌آید باید پاک‌سازی‌شده باشد، یا حداقل مطمئن شوید محتوای کاربری هرگز شامل HTML اجرایی نیست.

## اندپوینت‌های افزوده‌شده در بازبینی نهایی

پنج قابلیت فقط در `localStorage` زندگی می‌کردند و هیچ مسیری نداشتند. یعنی بعد از اتصال سرور، همچنان در مرورگر می‌ماندند و هر اپراتور داده متفاوتی می‌دید.

### مجوز دانلود

```
POST /commerce/entitlements   →  ["acc-101", "acc-102"]
```

فهرست محصولاتی که این کاربر حق دانلودشان را دارد.

**مهم:** قبلاً از کلید `irHesabdarPurchasedProducts` در مرورگر خوانده می‌شد. یعنی:

- کاربری که پول داده بود، در مرورگر دیگر دسترسی نداشت
- هر کسی با یک خط در کنسول، قفل همه فایل‌ها را باز می‌کرد

**سرور باید این را از جدول سفارش‌ها بسازد** و هرگز به فهرستی که کلاینت می‌فرستد اعتماد نکند.

### اعلان‌ها

```
GET    /admin/notifications
POST   /admin/notifications              // idempotent روی id
PATCH  /admin/notifications/:id/read
DELETE /admin/notifications/:id
DELETE /admin/notifications              // حذف همه
```

**نکته امنیتی:** قانون دسترسی باید سمت سرور اعمال شود. ردیف‌های `staff` و `report` **نباید اصلاً** برای نقش «ادمین» ارسال شوند. فیلتر سمت کلاینت فقط برای نمایش است.

### سابقه تغییرات کارکنان

```
GET  /admin/audit/:staffId
POST /admin/audit/:staffId
```

سند تغییرات پروفایل مدیران و ادمین‌هاست. باید فقط-افزودنی باشد و از مرورگری که در آن ساخته شده جان سالم به در ببرد.

### آیتم‌های محتوای سایت

```
GET    /admin/content-items
POST   /admin/content-items       // ۴۰۹ برای شناسه تکراری
DELETE /admin/content-items/:id
```

## نکته درباره نوشتن دوتایی

پنل برای سرعت نمایش، اعلان و سابقه را همزمان در حافظه محلی و روی سرور می‌نویسد. برای همین **مسیرهای POST باید idempotent باشند**:

- اعلان: بر اساس `id`
- سابقه: بر اساس `date` + `text`

اگر سرور این را رعایت نکند، هر رویداد دوبار ثبت و دوبار شمرده می‌شود.
