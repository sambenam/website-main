# تب سفارشات — گزارش و تغییرات

## خواسته

> هر کاربری هر نوع خریدی انجام داد — چه موفق چه ناموفق — بیاد اینجا قرار بگیره

---

## آنچه پیدا شد

### ۱. فقط خرید موفق ثبت می‌شد

`recipt.js` سفارش را داخل شرط `if (status === "success")` می‌ساخت. خرید ناموفق هیچ ردی در پنل نمی‌گذاشت.

### ۲. پرداخت هرگز شکست نمی‌خورد

مسیر `/commerce/payment` همیشه `status: "success"` برمی‌گرداند. یعنی حتی راهی برای تست حالت ناموفق وجود نداشت.

### ۳. سفارش از `appApi` رد نمی‌شد

`recipt.js` مستقیم در `localStorage` می‌نوشت — تنها جای باقی‌مانده در کل پروژه.

### ۴. دو انبار جدا

```
api.js     →  hesabyarApiState.orders
recipt.js  →  irHesabdarOrders        ← فقط این یکی را پنل می‌خواند
```

### ۵. داده‌های ساختگی

نام خریدار پیش‌فرض «سام به‌نام»، ایمیل `sam@example.com`، و تاریخ شمسی با `getFullYear() - 19` که فقط بخشی از سال درست است.

### ۶. مبلغ رشته بود

`"۴۹,۰۰۰ تومان"` ذخیره می‌شد، نه عدد. جمع‌زدن برای گزارش درآمد از آن ممکن نبود.

## آنچه انجام شد

### جریان جدید

```
پرداخت موفق    →  createPayment()      →  status: success
پرداخت ناموفق  →  createPayment()      →  status: failed    + دلیل
انصراف کاربر   →  recordCancelled()    →  status: cancelled
```

هر سه در یک انبار (`irHesabdarOrders`) می‌نشینند و پنل همه را نشان می‌دهد.

### شکل سفارش

```json
{
  "id": "#۱۰۰۰۱",
  "userId": "user-abc",
  "customer": "سام به‌نام",
  "buyerEmail": "sam@example.com",
  "buyerPhone": "09121112233",
  "product": "دوره حسابداری مقدماتی",
  "productId": "acc-101",
  "items": [{ "id": "acc-101", "name": "...", "price": 49000 }],
  "amount": 49000,
  "status": "success",
  "failureReason": null,
  "date": "۱۴۰۵/۰۵/۰۵",
  "createdAt": "2026-07-27T17:00:00.000Z"
```

| تغییر  | قبل                  | بعد                            |
| ------ | -------------------- | ------------------------------ |
| مبلغ   | `"۴۹,۰۰۰ تومان"`     | `49000`                        |
| تاریخ  | `getFullYear() - 19` | `Intl.DateTimeFormat("fa-IR")` |
| شماره  | تصادفی، قابل تکرار   | ترتیبی از `nextOrderNumber()`  |
| خریدار | پیش‌فرض ساختگی       | از فرم پرداخت                  |

### در پنل

- **کادر خلاصه** بالای جدول: کل سفارش‌ها، موفق، ناموفق، لغو شده، و درآمد
- **درآمد فقط از پرداخت‌های موفق** جمع می‌شود
- **دلیل ناموفقی** زیر برچسب وضعیت
- **فیلتر** با گزینه‌های تازه (موفق / ناموفق / لغو شده / در حال پردازش)
- **رنگ مبلغ** فقط برای پرداخت موفق سبز است
- **حالت خالی** وقتی فیلتری نتیجه ندارد

### کلید تست

در صفحه درگاه یک تیک اضافه شد:

```
☐ شبیه‌سازی پرداخت ناموفق (فقط برای تست)
```

با آن می‌توانید بدون درگاه واقعی، حالت ناموفق را در پنل ببینید.

> این بخش با `BACKEND NOTE` علامت خورده و باید هنگام اتصال درگاه واقعی حذف شود.

## سهم بک‌اند‌کار

### اندپوینت پرداخت

```
POST /api/commerce/payment
بدنه: { amount, buyer: {name,email,phone}, items: [...] }

موفق:   200  { success: true, orderId, status: "success", order }
ناموفق: 402  { message, details: { orderId, order } }
```

⚠️ **مهم:** پرداخت ناموفق هم باید سفارش را با `status: "failed"` ثبت کند و `orderId` را در پاسخ خطا برگرداند. فرانت‌اند با همان شناسه، کاربر را به صفحه رسید می‌فرستد.

### اندپوینت انصراف

```
POST /api/commerce/cancelled
بدنه: { amount, buyer, items }
پاسخ: { success: true, orderId, status: "cancelled" }
```

وقتی کاربر بدون پرداخت از درگاه خارج می‌شود.

### مسیرهای مدیریتی

```
GET   /api/admin/orders
PATCH /api/admin/orders/:id/status
```

### نکات

- `amount` را **عدد** برگردانید، نه رشته قالب‌بندی‌شده
- شماره سفارش را سرور تولید کند تا یکتا بماند
- تأیید پرداخت باید از **درگاه** بیاید، نه از کلاینت — وگرنه کسی می‌تواند با دستکاری درخواست، سفارش موفق جعلی بسازد
- `userId` را از توکن سشن بگیرید، نه از بدنه درخواست

# اتصال تب سفارشات به بقیه پروژه

پس از بررسی، سه شکاف پیدا و رفع شد:

## ۱. داشبورد

| کارت         | قبل                              | بعد                       |
| ------------ | -------------------------------- | ------------------------- |
| درآمد کل     | فقط موفق‌ها ✅                   | همان، ولی با محاسبه مشترک |
| سفارشات جدید | **همه**، شامل ناموفق و لغوشده ❌ | فقط پرداخت‌های موفق ✅    |

کارت «سفارشات جدید» ناموفق‌ها را هم می‌شمرد و عدد را متورم می‌کرد.

## ۲. تب آنالیز — یک باگ پنهان

هفت جای این تب مبلغ را با این الگو می‌خواندند:

```js
String(o.amount).replace(/[^d.]/g, "");
```

بک‌اسلش جا افتاده بود. `[^d.]` یعنی «هر چیزی جز حرف d و نقطه» — پس تمام ارقام حذف می‌شدند و نتیجه همیشه `NaN` بود.

```
ورودی "49000"  →  با [^d.]   →  ""      →  NaN
ورودی "49000"  →  با [^\d.]  →  "49000" →  49000
```

یعنی **میانگین سبد خرید، نمودار درآمد ماهانه و گزارش‌های آنالیز همگی صفر نشان می‌دادند**. هر هفت مورد با تابع مشترک `orderAmountValue` جایگزین شد.

## ۳. پروفایل کاربر در سایت

تب «سفارش‌های من» ردیف‌های ثابت و ساختگی داشت — خریدهای ۲۵ میلیون تومانی در سایتی که محصولش ۴۹ هزار تومان است.

حالا از `appApi.commerce.myOrders()` داده واقعی می‌خواند و هر سه وضعیت را نشان می‌دهد. کاربر می‌بیند پرداختش ناموفق بوده، به‌جای اینکه فکر کند پولش گم شده.

### نشت حریم خصوصی که حین تست پیدا شد

سفارش با ایمیل شخص دیگر، به حساب کاربر واردشده می‌چسبید. حالا `userId` فقط وقتی ثبت می‌شود که ایمیل صورتحساب با ایمیل حساب یکی باشد.

## توابع مشترک

برای اینکه سه بخش هرگز اعداد متفاوت نشان ندهند:

| تابع                       | کار                                              |
| -------------------------- | ------------------------------------------------ |
| `orderAmountValue(amount)` | خواندن مبلغ، چه عدد چه رشته قدیمی با ارقام فارسی |
| `calculateRevenue(orders)` | جمع مبلغ سفارش‌های موفق                          |

## اندپوینت جدید برای بک‌اند

```
POST /api/commerce/my-orders
پاسخ: آرایه سفارش‌های همان کاربر
```

⚠️ سرور باید کاربر را از **توکن سشن** تشخیص دهد، نه از بدنه درخواست. وگرنه هر کسی می‌تواند با فرستادن ایمیل دیگری، سفارش‌های او را ببیند.

# دکمه دانلود گزارش

**بله کار می‌کند.** فایل CSV واقعی می‌سازد و مرورگر آن را دانلود می‌کند. با شبیه‌سازی کامل مرورگر تست شد و محتوای فایل بررسی گردید.

نمونه خروجی:

```csv
"شماره سفارش","نام خریدار","موبایل","ایمیل","محصول","مبلغ","تاریخ","وضعیت","توضیح"
"#۱۰۰۰۱","سام به‌نام","۰۹۱۲۱۱۱۲۲۳۳","sam@t.com","دوره","۴۹,۰۰۰ تومان","۱۴۰۵/۰۵/۰۵","پرداخت موفق",""
"#۱۰۰۰۲","مریم حسینی","۰۹۳۵۴۴۴۵۵۶۶","m@t.com","پکیج","۲۵۰,۰۰۰ تومان","۱۴۰۵/۰۵/۰۴","پرداخت ناموفق","موجودی کافی نیست"
```

## سه مشکلی که حین بررسی رفع شد

### ۱. نام فایل با ارقام فارسی

```
قبل:  report_orders_۱۷۸۵۱۷۸۲۶۸۸۱۹.csv
بعد:  orders-report-2026-07-27.csv
```

ویندوز و برخی سرویس‌های ابری با نام فایل غیرلاتین مشکل دارند. ضمناً تاریخ خوانا بهتر از عدد میلی‌ثانیه است.

### ۲. تزریق فرمول در اکسل

اگر نام محصولی با `=` یا `+` یا `-` یا `@` شروع شود، اکسل آن را **فرمول** حساب می‌کند نه متن:

```
نام محصول:  =HYPERLINK("http://bad.site","برنده شدید")
در اکسل:    یک لینک قابل کلیک در فایل مدیر
```

حالا چنین مقادیری با یک آپستروف ابتدایی خنثی می‌شوند.

### ۳. کوتیشن داخل مقدار

اگر نام محصول کوتیشن داشت، ستون‌های بعدی جابه‌جا می‌شدند. حالا طبق استاندارد CSV دوبل می‌شود.

## یکسان‌سازی

هر چهار خروجی پروژه (گزارش سفارشات، فاکتور تکی، گزارش درآمد، پرفروش‌ها) حالا از یک مسیر مشترک عبور می‌کنند:

| تابع                                | کار                     |
| ----------------------------------- | ----------------------- |
| `csvCell(value)`                    | امن‌سازی یک خانه        |
| `csvRow(values)`                    | ساخت یک سطر             |
| `triggerCsvDownload(content, name)` | تحویل فایل با نام لاتین |

`URL.revokeObjectURL` هم اضافه شد تا فایل موقت در حافظه نماند.

## نکته درباره BOM

فایل با `\uFEFF` شروع می‌شود تا اکسل حروف فارسی را درست بخواند. بدون آن، متن فارسی به‌صورت `Ø³Ø§Ù…` نمایش داده می‌شود. این از قبل درست بود.
