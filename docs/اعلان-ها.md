# اعلان‌ها و نوتیف‌ها

هفت منبع رویداد به زنگوله و تب اعلان‌ها وصل شده‌اند.

---

## منابع

| رویداد                      | نوع        | از کجا می‌آید            | چه کسی می‌بیند |
| --------------------------- | ---------- | ------------------------ | -------------- |
| ثبت سفارش                   | `purchase` | تب سفارشات / پرداخت سایت | همه            |
| پرداخت موفق                 | `purchase` | همان                     | همه            |
| پرداخت ناموفق               | `purchase` | همان                     | همه            |
| ثبت‌نام کاربر جدید          | `user`     | فرم ثبت‌نام سایت         | همه            |
| تغییر پروفایل ادمین یا مدیر | `staff`    | تب پروفایل               | فقط مدیرها     |
| حذف ادمین توسط مدیر         | `deletion` | مدیریت دسترسی‌ها         | همه            |
| گزارش تخلف                  | `report`   | فرم تماس با ما / قوانین  | فقط مدیرها     |

---

## باگ اصلی که رفع شد

اعلان‌ها فقط از رویداد `storage` ساخته می‌شدند:

```js
window.addEventListener("storage", ...)
```

این رویداد را مرورگر **فقط در تب‌های دیگری که همان لحظه باز هستند** صدا می‌زند. یعنی:

- مشتری شب خرید می‌کرد → صبح که پنل را باز می‌کردید، **هیچ اعلانی نبود**
- کاربر ثبت‌نام می‌کرد و پنل بسته بود → هیچ ردی نمی‌ماند

تست واقعی قبل از رفع، با یک سفارش و یک ثبت‌نام در حالت بسته بودن پنل:

```
کل اعلان‌ها: ۰   ❌
```

**راه‌حل:** تابع `reconcileNotifications()` هنگام باز شدن پنل همه منابع را می‌خواند و هر رویدادی که هنوز اعلام نشده را اعلان می‌کند. یک دفتر «اعلام‌شده‌ها» در `irHesabdarAnnouncedEvents` جلوی تکرار را می‌گیرد.

```
بعد از رفع → purchase: ۱، user: ۱  ✅
رفرش دوباره → همان ۲ تا، بدون تکرار  ✅
```

### باگ دوم: بج زنگوله هیچ‌وقت عدد نمی‌گرفت

المان `notifBadge` در HTML بود ولی **هیچ کدی به آن نمی‌نوشت**، پس همیشه مخفی می‌ماند. حالا `updateNotificationBadge()` تعداد خوانده‌نشده‌ها را می‌نویسد — و فقط آن‌هایی را می‌شمارد که کاربر فعلی حق دیدنشان را دارد.

## گزارش تخلف

### فرم

در صفحه `support.html` (همان صفحه‌ای که «تماس با ما» و «قوانین» به آن می‌روند)، زیر فرم ارسال پیام:

- نام و ایمیل (برای کاربر لاگین‌کرده خودکار پر می‌شود)
- نوع تخلف: محتوای نامناسب / نقض حق نشر / سوءاستفاده / کلاهبرداری / سایر
- درجه اهمیت: کم / متوسط / زیاد
- مورد گزارش‌شده
- بارگذاری مدرک — فقط تصویر، حداکثر ۳۰۰ کیلوبایت (اختیاری)
- شرح تخلف

### مسیر

```
کاربر فرم را پر می‌کند
        ↓
POST /support/reports
        ↓
ذخیره در irHesabdarReports با شناسه RPT-1041
        ↓
پنل باز می‌شود → اعلان «گزارش تخلف جدید»
        ↓
فقط مدیرها می‌بینند
```

گزارش‌ها **جدا از پیام‌ها** ذخیره می‌شوند. پیام یک گفتگوست، گزارش یک پرونده رسیدگی.

---

## قانون دسترسی

```js
canReceiveNotification(n); // ادمین: staff و report را نمی‌بیند
```

نکته مهم: **ساختن رکورد** و **اجازه دیدن** دو چیز جدا هستند. اعلان همیشه ساخته و ذخیره می‌شود؛ فیلتر فقط موقع نمایش اعمال می‌شود. اگر این‌طور نبود، تغییر پروفایل توسط ادمین هرگز ثبت نمی‌شد و مدیر خبردار نمی‌شد.

## برای بک‌اند

```js
GET   /admin/notifications
GET   /admin/reports
PATCH /admin/reports/:id/status     { status: "reviewed" }
POST  /support/reports              // از سایت
```

**نکته امنیتی:** سرور باید ردیف‌های `staff` و `report` را برای ادمین‌ها **اصلاً نفرستد**. فیلتر سمت کلاینت فقط برای نمایش است.

### شکل گزارش

```js
{
  id: "RPT-1041",
  reporterId: "user-x9",        // null برای مهمان
  reporterName: "علی احمدی",
  reporterEmail: "ali@t.com",
  kind: "content",              // content|copyright|abuse|fraud|other
  severity: "high",             // low|medium|high
  subject: "دوره حسابداری مقدماتی",
  description: "...",
  evidenceImage: "data:image/png;base64,...",   // فقط تصویر
  status: "pending",            // pending|reviewed
  date: "۱۴۰۵/۰۵/۰۶",
  createdAt: "2026-07-28T..."
}
```

### کلیدهای ذخیره‌سازی

```
irHesabdarNotifications      اعلان‌ها (حداکثر ۲۰۰ مورد اخیر)
irHesabdarReports            گزارش‌های تخلف
irHesabdarAnnouncedEvents    دفتر رویدادهای اعلام‌شده، جلوگیری از تکرار
```

## دو اصلاح ظاهری و کاربردی

### منوهای بازشو خوانا نبودند

عنصر `<option>` را مرورگر با رنگ‌های خودِ `<select>` می‌کشد. رنگ متن `--text-primary` یعنی `#f1f5f9` (تقریباً سفید) روی پس‌زمینه `rgba(255,255,255,0.05)` که تقریباً شفاف است — یعنی **سفید روی سفید**. در حالت روز هم به فهرست خام سیستم‌عامل برمی‌گشت.

فرم «تماس با ما» این مشکل را نداشت چون منوی موضوعش با جاوااسکریپت به یک فهرست سفارشی تبدیل می‌شد. آن سازنده اما فقط برای همان یک فیلد نوشته شده بود.

حالا تابع `enhanceSelect()` عمومی شده و هر سه منو (موضوع، نوع تخلف، درجه اهمیت) را می‌سازد — با آیکون رنگی برای هر گزینه و پشتیبانی کامل از حالت روز و شب. یک لایه پشتیبان هم برای `<option>` خام گذاشته شد تا اگر جاوااسکریپت اجرا نشد، باز هم خوانا بماند.

### لینک شواهد → بارگذاری مدرک

لینک به‌راحتی اشتباه وارد می‌شود، ممکن است از کار بیفتد، و می‌تواند به هر جایی اشاره کند. حالا کاربر خود تصویر را پیوست می‌کند.

- فقط تصویر: `JPG`، `PNG`، `WebP`، `GIF`
- حداکثر ۳۰۰ کیلوبایت
- پیش‌نمایش بلافاصله نمایش داده می‌شود، با دکمه حذف

نوع فایل از روی **MIME واقعی** بررسی می‌شود نه پسوند، پس تغییر نام یک `.pdf` به `.jpg` رد می‌شود.

**نکته برای بک‌اند:** تصویر فعلاً به شکل data URL ارسال می‌شود چون اندپوینت آپلود وجود ندارد. هنگام اتصال سرور، `POST /support/reports/evidence` بسازید که مسیر فایل را برگرداند — و همین بررسی‌های نوع و حجم را **سمت سرور هم** تکرار کنید. بررسی سمت کلاینت جلوی اشتباه کاربر را می‌گیرد، نه کسی که عمداً دور بزند.

## حذف اعلان و پیام

کنار هر اعلان و هر گفتگو یک دکمه حذف اضافه شد. هر دو قبل از حذف تأیید می‌گیرند، چون بازگشتی ندارند و دکمه کنار «پاسخ» است.

دکمه «حذف همه» بالای تب اعلان‌ها فقط مواردی را پاک می‌کند که **همان کاربر اجازه دیدنشان را دارد**. یعنی اگر ادمینی همه را پاک کند، اعلان‌های `staff` و `report` که مخصوص مدیرهاست دست‌نخورده می‌ماند.

پیام حذف‌شده از هر دو انبار پاک می‌شود (`irHesabdarMessages` و state داخلی API)، وگرنه در ادغام بعدی دوباره ظاهر می‌شد.

## پاسخ به گزارش تخلف

روی اعلان گزارش تخلف که کلیک کنید، دکمه **«پاسخ به کاربر»** هست. یک پنجره باز می‌شود با:

- خلاصه گزارش (شناسه، گزارش‌دهنده، مورد گزارش‌شده، شرح) تا لازم نباشد پنجره را ببندید
- کادر متن پاسخ
- انتخاب وضعیت رسیدگی: پاسخ داده شد / بررسی و بسته شد / همچنان در حال بررسی
- پیوست تصویر، اختیاری، فقط عکس تا ۳۰۰ کیلوبایت

### پاسخ کجا می‌رود

```
POST /admin/reports/:id/reply
        ↓
یک نخ گفتگوی معمولی با شناسه msg-RPT-1041 ساخته می‌شود
        ↓
حباب اول: شرح گزارش کاربر
حباب دوم: پاسخ مدیر
        ↓
در «پیام‌های من» پروفایل کاربر + تب پیام‌های پنل
```

**چرا کانال جدا نساختم:** اگر پاسخ گزارش جای دیگری می‌رفت، کاربر باید دو جا را چک می‌کرد و ما دو صندوق را همگام نگه می‌داشتیم. حالا کاربر همه گفتگوهایش را یک‌جا می‌بیند.

پاسخ دوم به همان گزارش، به همان نخ اضافه می‌شود و نخ تکراری نمی‌سازد.

## یک حفره امنیتی که موقع کار بسته شد

اندپوینت `/support/my-messages` ایمیل را از بدنه درخواست هم می‌پذیرفت:

```js
const email = session?.user?.email || body.email; // ← خطرناک
```

یعنی هر کسی می‌توانست با فرستادن ایمیل شخص دیگر، **تاریخچه پیام‌های او را بخواند**. حالا فقط ایمیل روی سشن معتبر است.

## آنچه هنوز مانده

- **تب مدیریت گزارش‌ها** — گزارش‌ها به اعلان تبدیل می‌شوند ولی صفحه‌ای برای بررسی و بستن پرونده ندارند. اندپوینت `setStatus` آماده است.
- **نشانی IP** در جزئیات اعلان‌ها تا اتصال سرور خالی است.
