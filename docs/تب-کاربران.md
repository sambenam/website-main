# تب کاربران — تقسیم کار فرانت‌اند و بک‌اند

---

## وضعیت فعلی

کاربری که در سایت ثبت‌نام می‌کند، **الان** در تب کاربران پنل ظاهر می‌شود. کل جریان روی mock کار می‌کند و ۱۲ تست پوششش می‌دهد.

```
کاربر فرم ثبت‌نام را پر می‌کند  (نام · ایمیل · رمز)
        ↓
appApi.auth.register({ name, email, password })
        ↓
ذخیره با role: "کاربر عادی" · status: "فعال" · createdAt
        ↓
پنل باز می‌شود ← appApi.admin.users.list()
        ↓
ردیف کاربر در جدول
```

### تلفن همراه

فرم ثبت‌نام تلفن نمی‌پرسد تا کوتاه بماند. کاربر بعداً آن را در صفحه پروفایل وارد می‌کند و همان لحظه در ستون تلفن پنل ظاهر می‌شود:

```
کاربر → صفحه پروفایل → تلفن را وارد می‌کند
        ↓
appApi.profile.update({ phone })
        ↓
ستون تلفن در پنل به‌روز می‌شود
```

ستون تا آن زمان `—` نشان می‌دهد.

## سهم شما (فرانت‌اند) — انجام شده ✅

| کار                                          | وضعیت                            |
| -------------------------------------------- | -------------------------------- |
| ثبت‌نام کوتاه: نام، ایمیل، رمز               | ✅                               |
| دریافت تلفن از صفحه پروفایل و رساندنش به پنل | ✅                               |
| ثبت `role`، `status` و `createdAt`           | ✅                               |
| ستون «تاریخ عضویت» در جدول پنل               | ✅                               |
| نمایش کاربران سایت در کنار کاربران دستی      | ✅                               |
| تغییر وضعیت کاربر سایت از پنل                | ✅ رفع شد (قبلاً ۴۰۴ می‌داد)     |
| حذف کاربر + حذف اعتبارنامه ورود              | ✅ رفع شد (قبلاً کاربر برمی‌گشت) |
| پشتیبانی از شناسه رشته‌ای در دکمه ویرایش     | ✅ رفع شد                        |
| جستجو در جدول                                | ✅ از قبل کار می‌کرد             |

### پنج باگی که پیدا و رفع شد

۱. **مدیریت کاربران سایت کار نمی‌کرد.** تغییر وضعیت `404` برمی‌گرداند و حذف بی‌اثر بود، چون این کاربران فقط خوانده می‌شدند و هرگز در انبار پنل نوشته نمی‌شدند. حالا موقع اولین تغییر، رکورد به انبار پنل کپی می‌شود.

۲. **کاربر حذف‌شده برمی‌گشت.** حذف فقط از انبار پنل پاک می‌کرد، ولی `GET` دوباره از انبار احراز هویت می‌خواندش. بدتر اینکه کاربر حذف‌شده هنوز می‌توانست لاگین کند.

۳. **دکمه ویرایش برای کاربران سایت خطا می‌داد.** شناسه بدون کوتیشن در `onclick` قرار می‌گرفت. برای شناسه عددی مشکلی نبود، ولی شناسه‌های سایت به شکل `user-f6dc9038-...` هستند و کد نامعتبر تولید می‌شد.

۴. **تلفن پس از ویرایش پروفایل به پنل نمی‌رسید.** ادغام، ردیف انبار پنل را کامل روی داده زنده می‌نوشت و یک عکس قدیمی را تثبیت می‌کرد. حالا انبار پنل فقط `status` و `role` را مالک است؛ نام، ایمیل، تلفن و تاریخ عضویت همیشه از خود حساب می‌آیند.

۶. **حساب غیرفعال همچنان می‌توانست وارد شود.** غیرفعال کردن کاربر در پنل هیچ اثری روی ورود نداشت. حالا `/auth/login` با کد ۴۰۳ رد می‌کند.

۵. **تاریخ عضویت گم می‌شد.** در `api.js` ثبت می‌شد ولی هنگام تحویل به پنل حذف می‌شد.

## سهم بک‌اند‌کار

سه اندپوینت. قرارداد کامل در `docs/API_CONTRACT.md`.

### `GET /api/admin/users`

```json
[
  {
    "id": "user-a1b2c3",
    "name": "نگین رضایی",
    "email": "negin@example.com",
    "phone": "09121112233",
    "role": "کاربر عادی",
    "status": "فعال",
    "createdAt": "2026-07-27T09:15:00.000Z",
    "source": "site"
  }
]
```

| فیلد        | توضیح                                                  |
| ----------- | ------------------------------------------------------ |
| `id`        | رشته یا عدد — فرانت هر دو را می‌پذیرد                  |
| `role`      | `کاربر عادی` · `ادمین` · `مدیر سایت` · `مدیر سیستم`    |
| `status`    | `فعال` · `غیرفعال`                                     |
| `createdAt` | ISO 8601 — برای ستون تاریخ عضویت                       |
| `source`    | `site` (ثبت‌نام در سایت) یا `admin` (ساخته‌شده در پنل) |

### `POST /api/admin/users`

برای دکمه «افزودن کاربر» در پنل.

بدنه: `{ name, email, phone, role }`
پاسخ: کاربر ساخته‌شده با `id`، `createdAt` و `source: "admin"`

⚠️ ایمیل تکراری باید `409` بدهد — چه با کاربر دیگری در پنل تداخل داشته باشد، چه با حسابی که در سایت ثبت‌نام کرده.

### `PATCH /api/admin/users/:id/status`

بدنه: `{ "status": "غیرفعال" }`
پاسخ: آبجکت کاربر به‌روزشده

⚠️ **مهم:** کاربر با وضعیت `غیرفعال` نباید بتواند لاگین کند. الان mock این را رعایت می‌کند و تست هم دارد.

### `DELETE /api/admin/users/:id`

پاسخ: `{ "success": true }`

⚠️ حذف باید اعتبارنامه ورود را هم پاک کند، نه فقط ردیف جدول را.

### مواردی که فقط سرور می‌تواند انجام دهد

| مورد                          | چرا                                      |
| ----------------------------- | ---------------------------------------- |
| احراز هویت مسیرهای `/admin/*` | کلاینت قابل دستکاری است                  |
| بررسی نقش در هر درخواست       | نقشی که مرورگر می‌فرستد قابل اعتماد نیست |
| هش کردن رمز (bcrypt / argon2) | الان متن ساده در localStorage است        |
| یکتا بودن ایمیل               | اعتبارسنجی سمت کلاینت فقط UX است         |
| صفحه‌بندی                     | با چند هزار کاربر، `GET` کامل کند می‌شود |

## سطوح دسترسی

دو سطح در پنل وجود دارد و نقش از سشن ورود خوانده می‌شود:

| نقش                        | تب کاربران                                            |
| -------------------------- | ----------------------------------------------------- |
| `مدیر سایت` · `مدیر سیستم` | دسترسی کامل                                           |
| `ادمین`                    | فقط شناسه، نام و ایمیل — تلفن پوشانده، ویرایش غیرفعال |

### آنچه برای «ادمین» محدود می‌شود

- **شماره تلفن** به شکل `۰۹۱۲•••••` نمایش داده می‌شود. ارقام واقعی اصلاً وارد صفحه نمی‌شوند، پس با ابزار توسعه‌دهنده هم قابل بازیابی نیستند.
- **دکمه ویرایش** غیرفعال است و آیکون قفل دارد.
- **فراخوانی مستقیم `editUser()`** از کنسول هم رد می‌شود.
- **جستجو بر اساس تلفن** کار نمی‌کند. اگر کار می‌کرد، ادمین می‌توانست با تایپ ارقام و دیدن اینکه کدام ردیف باقی می‌ماند، شماره را حدس بزند.
- یک نوار توضیحی بالای جدول می‌گوید چرا کنترل‌ها خاکستری‌اند.

### تست دستی

```js
// نقش را عوض کنید و صفحه را رفرش کنید
const s = JSON.parse(localStorage.getItem("hesabyarSession"));
s.user.role = "ادمین"; // یا "مدیر سایت"
localStorage.setItem("hesabyarSession", JSON.stringify(s));
location.reload();
```

### سهم بک‌اند

⚠️ این محدودیت‌ها فقط ظاهر را شکل می‌دهند. هر کسی می‌تواند در ابزار توسعه‌دهنده مقدار نقش را عوض کند.

سرور باید همین سیاست را اعمال کند:

- در `GET /api/admin/users`، برای حساب `ادمین` فیلد `phone` را **اصلاً نفرستد** (یا پوشانده بفرستد)
- `PATCH /api/admin/users/:id/status` و `DELETE /api/admin/users/:id` را برای `ادمین` با کد `403` رد کند
- نقش را از توکن سشن بخواند، نه از بدنه درخواست

## چیزهایی که هنوز نیستند

هیچ‌کدام مانع کار نیستند، ولی خوب است بدانید:

| مورد                         | توضیح                                                                                                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **صفحه‌بندی**                | همه کاربران یکجا رندر می‌شوند. با چند صد کاربر کند می‌شود.                                                                                                                                  |
| **فیلتر وضعیت**              | فقط جستجوی متنی داریم؛ فیلتر «فقط غیرفعال‌ها» نیست.                                                                                                                                         |
| **مرتب‌سازی ستون‌ها**        | کلیک روی سرستون کاری نمی‌کند.                                                                                                                                                               |
| **خروجی CSV**                | برای سفارشات هست، برای کاربران نه.                                                                                                                                                          |
| **سفارش‌های کاربر در مودال** | `renderUserOrders` سفارش را با تطبیق **نام** یا ایمیل پیدا می‌کند. برای کاربران سایت که هنوز خریدی نکرده‌اند خالی است، و تطبیق بر اساس نام شکننده است — بهتر است سفارش `userId` داشته باشد. |

### درباره آخری

```js
// امروز
orders.filter((o) => o.customer === user.name || o.buyerEmail === user.email);

// بهتر (نیازمند تغییر ساختار سفارش)
orders.filter((o) => o.userId === user.id);
```

اگر دو کاربر هم‌نام باشند، سفارش‌هایشان قاطی می‌شود. وقتی به تب سفارشات رسیدیم این را درست می‌کنیم.
