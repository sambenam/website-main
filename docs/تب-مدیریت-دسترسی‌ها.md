# تب مدیریت دسترسی‌ها — تقسیم کار

---

## سلسله‌مراتب

| رتبه | نقش                        | توضیح                   |
| ---- | -------------------------- | ----------------------- |
| ۱    | `مدیر سایت` · `مدیر سیستم` | دسترسی کامل             |
| ۲    | `ادمین`                    | فقط مشاهده در این تب    |
| ۳    | `کاربر عادی`               | در تب کاربران، نه اینجا |

## قواعد

۱. **فقط مدیر** می‌تواند مدیر یا ادمین اضافه کند، نقش عوض کند، یا حساب حذف کند
۲. **مدیر می‌تواند مدیر دیگری اضافه کند** — بک‌اند فقط مدیر _اول_ را می‌سازد تا نقطه شروعی وجود داشته باشد
۳. **آخرین مدیر حذف یا تنزل نمی‌شود** — وگرنه سامانه برای همیشه قفل می‌شود
۴. **از این تب فقط مدیر و ادمین اضافه می‌شود** — کاربر عادی از راه ثبت‌نام در سایت می‌آید

قاعده سوم در **دو لایه** اعمال شده: هم در رابط کاربری، هم در خود `appApi`. اگر کسی رابط را دور بزند و مستقیم API را صدا کند، باز هم `409` می‌گیرد.

### چهار مشکلی که پیدا و رفع شد

**۱. تب «مدیریت دسترسی‌ها» اصلاً دسترسی را مدیریت نمی‌کرد.**
مودال ویرایش فقط فیلد وضعیت داشت. هیچ راهی برای تغییر نقش کسی وجود نداشت — با اینکه اسم تب همین بود.

**۲. پنل نمی‌دانست چه کسی وارد شده.**

```js
let currentStaffProfileId = 1; // هاردکد
```

یعنی هر عملی که ثبت می‌شد، به نام کاربر شماره ۱ نوشته می‌شد. حالا از سشن و بر اساس ایمیل پیدا می‌شود.

**۳. هیچ بررسی رتبه‌ای نبود.**
`editStaff` و دکمه حذف روی `window` هستند. دکمه در رابط مخفی می‌شد، ولی از کنسول قابل صدا زدن بود:

```js
editStaff(1); // ادمین، حساب مدیر را باز می‌کرد
```

حالا خود توابع هم بررسی می‌کنند.

**۴. امکان قفل شدن دائمی سامانه.**
اگر تنها مدیر، حساب خودش را حذف می‌کرد، هیچ‌کس دیگر نمی‌توانست نقش‌ها را مدیریت کند. راه بازگشتی هم وجود نداشت.

**۵. سشن حالت توسعه، نقش را خراب می‌کرد.**
وقتی گیت احراز هویت خاموش است، پنل یک سشن با `role: "admin"` می‌ساخت. کد جدید این مقدار را به‌عنوان سطح _محدود_ می‌خواند، پس اپراتور بی‌صدا دسترسی مدیریتش را از دست می‌داد. حالا نام فارسی نقش نوشته می‌شود.

## سهم بک‌اند‌کار

### ۱. تعیین مدیر اول ⚠️

این کار فقط از سرور برمی‌آید. پنل عمداً امکان ساخت مدیر را ندارد.

روش پیشنهادی — یک seed هنگام راه‌اندازی:

```sql
INSERT INTO users (name, email, password_hash, role, status)
VALUES ('مدیر سایت', 'admin@yoursite.ir', '<hash>', 'مدیر سایت', 'فعال');
```

یا از طریق متغیر محیطی در اولین اجرا:

```
INITIAL_ADMIN_EMAIL=admin@yoursite.ir
INITIAL_ADMIN_PASSWORD=<رمز قوی>
```

**نکته:** سرور باید تضمین کند همیشه حداقل یک مدیر وجود دارد.

### ۲. اندپوینت تغییر نقش

```
PATCH /api/admin/users/:id/role
```

بدنه: `{ "role": "ادمین" }`
پاسخ: کاربر به‌روزشده

مقادیر معتبر: `مدیر سایت` · `مدیر سیستم` · `ادمین` · `کاربر عادی`

**کدهای خطا:**

| کد    | شرایط                   |
| ----- | ----------------------- |
| `403` | درخواست‌کننده مدیر نیست |
| `403` | هدف یک مدیر دیگر است    |
| `409` | تنزل آخرین مدیر         |
| `404` | کاربر پیدا نشد          |
| `422` | نقش نامعتبر             |

### ۳. قواعدی که سرور باید تکرار کند

فرانت‌اند این‌ها را اعمال می‌کند ولی قابل دور زدن است:

- نقش را **از توکن سشن** بخوانید، نه از بدنه درخواست
- ادمین نباید بتواند `PATCH /role` یا `DELETE` بزند
- مدیر نباید بتواند روی مدیر دیگر عمل کند
- شمارش مدیران قبل از هر حذف یا تنزل
- برای حساب ادمین، فیلد `phone` را در پاسخ نفرستید

### ۴. نکته درباره تغییر نقش و سشن فعال

وقتی نقش کسی عوض می‌شود، سشن فعلی‌اش هنوز نقش قدیمی را دارد. سرور باید یکی از این دو را انجام دهد:

- سشن‌های آن کاربر را باطل کند (امن‌تر)
- یا نقش را در هر درخواست از پایگاه داده بخواند، نه از توکن

در حالت mock فعلی، نقش جدید در ورود بعدی اعمال می‌شود.

## تست

```bash
node tests/staff-access.test.js    # ۳۶ تست
node tests/integration.test.js     # ۶۷ تست
```

پوشش شامل: تلاش ادمین برای ویرایش از کنسول، تلاش مدیر برای دست زدن به مدیر دیگر، محافظت از آخرین مدیر در هر دو لایه، و انتقال نقش جدید به ورود بعدی.

### تست دستی

```js
// نقش خود را عوض کنید
const s = JSON.parse(localStorage.getItem("hesabyarSession"));
s.user.role = "ادمین"; // یا "مدیر سایت"
localStorage.setItem("hesabyarSession", JSON.stringify(s));
location.reload();
```
