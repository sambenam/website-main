# چک‌لیست تحویل به بک‌اندکار

پاسخ کوتاه: **بله، از سمت فرانت آماده تحویل است** — ولی سه نکته هست که بک‌اندکار باید بداند، و یک بخش عمداً ناتمام مانده.

---

## ✅ آنچه کامل است

### اتصال با دو خط تغییر

```html
<script>
  window.APP_CONFIG = {
    apiMode: "real",
    apiBaseUrl: "https://api.yoursite.com",
  };
</script>
<script src="../scripts/api.js"></script>
```

و سه خط موک را از هر صفحه پاک کنید:

```html
<script src="../scripts/api-mock-store.js"></script>
<script src="../scripts/api-mock-site.js"></script>
<script src="../scripts/api-mock-admin.js"></script>
```

هیچ فایل دیگری لازم نیست عوض شود. تست شده: در حالت `real` همه درخواست‌ها با متد و توکن و بدنه درست به سرور می‌روند و هیچ‌کدام به `localStorage` برنمی‌گردند.

### همه اندپوینت‌ها

```
احراز هویت    /auth/register  /auth/login  /auth/logout  /auth/me
              /auth/forgot-password

کاربر         /profile/update  /profile/password
              /commerce/my-orders      /commerce/entitlements
              /support/my-messages

خرید          /commerce/payment  /commerce/cancelled  /commerce/coupon

پشتیبانی      /support/messages  /support/reports
              /newsletter/subscribe

محتوا         /content/items/:id

پنل           /admin/users     /admin/products   /admin/orders
              /admin/messages  /admin/reports    /admin/settings
              /admin/notifications  /admin/audit/:staffId
              /admin/content-items  /admin/pending-changes
```

### رفتار خطا

- پاسخ ناموفق → `ApiError` با `status` و پیام سرور
- تایم‌اوت → کد `408`
- قطع ارتباط → کد `0`

هر صفحه‌ای که این‌ها را می‌گیرد، پیام را به کاربر نشان می‌دهد.

---

## ⚠️ سه نکتهٔ امنیتی که سرور باید رعایت کند

### ۱. مجوز دانلود را از جدول سفارش بساز

```
POST /commerce/entitlements  →  ["acc-101", "acc-102"]
```

**هرگز** به فهرستی که کلاینت می‌فرستد اعتماد نکن. این باید از سفارش‌های `success` همان کاربر ساخته شود.

### ۲. قانون دسترسی اعلان‌ها را سمت سرور اعمال کن

نقش «ادمین» **نباید** ردیف‌های `staff` و `report` را دریافت کند — نه اینکه دریافت کند و کلاینت پنهانش کند. فیلتر فعلی در مرورگر فقط برای نمایش است.

### ۳. حساب غیرفعال را در هر درخواست بررسی کن

فرانت این را چک می‌کند، ولی سرور هم باید. یک توکن معتبر از حسابی که بعداً مسدود شده، نباید بتواند خرید یا پیام ثبت کند.

### ۴. مبلغ و وضعیت پرداخت را از خود درگاه تأیید کن

الان وضعیت از پارامتر URL خوانده می‌شود که کاربر می‌تواند دستکاری کند. در نسخهٔ واقعی، callback درگاه باید سمت سرور تأیید شود.

## ❌ آنچه هنوز تمام نیست

### رمز عبور پنل

```js
// scripts/admin/auth.js
function verifyAdminPassword(input) { ... }
```

رمز فعلاً در `localStorage` است. این **عمدی و موقت** است و در سه جای کد `BACKEND NOTE` دارد.

بک‌اندکار باید:

```js
// به‌جای بدنهٔ فعلی:
return appApi.admin.auth.verifyPassword({ password: input });
```

بقیهٔ پنل فقط `verifyAdminPassword()` را صدا می‌زند، پس هیچ فایل دیگری تغییر نمی‌کند. سرور باید با `bcrypt` یا `argon2` هش کند.

### احراز هویت پنل خاموش است

```js
const ADMIN_AUTH_ENABLED = false; // scripts/admin/auth.js
```

برای توسعه خاموش شده. **قبل از انتشار حتماً `true` شود.**

### آپلود فایل

تصاویر فعلاً به شکل data URL منتقل می‌شوند چون اندپوینت آپلود وجود ندارد. لازم است:

```
POST /support/reports/evidence   →  { url: "..." }
POST /admin/products/image       →  { url: "..." }
```

و همان بررسی نوع و حجم که در کلاینت هست، سمت سرور هم تکرار شود.
